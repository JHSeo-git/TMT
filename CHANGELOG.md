# Changelog

## 2026-09-04 - The list shows every published item, grouped by year

- `getIssues` defaulted to one page of 100 and nothing ever asked for a second, so `/` listed the newest 100 of 293 published items and `generateStaticParams` prerendered the same 100. 193 items were on the site only if you already knew the number. The build now generates 298 pages rather than 105, and `/` carries 293 item links rather than 100.
- `getAllPublishedItems` replaces it and walks every page with `octokit.paginate`. That deleted the hand-rolled `Link` header parsing, which only ever looked for `&page=` and would have missed a `?page=` first parameter, and it keeps the `body` the old mapping threw away — the list endpoint returns it, so 293 full bodies now arrive in three requests instead of 293. The search index is built from exactly that.
- `nextIssueNo` and `prevIssueNo` were deleted rather than fixed. They were computed within a single page, so they broke at the 100-item boundary, and nothing has ever read them.
- The list renders all 293 in one page under a heading per year — 151 for 2026, 130 for 2025, 12 for 2024 — rather than paginating. This is an archive index; one scannable list is the honest presentation, and `⌘K` covers what pagination would otherwise be for. The row shape is unchanged: title left, right-aligned date, tabular numerals.
- `getAllPublishedItems` memoises its promise at module scope. That is load-bearing, not an optimisation: the root layout awaits it to give the palette its titles, and a layout renders once per route, so without the memo a build would repeat three GitHub requests for every one of 298 pages.

## 2026-09-04 - The publish gate is checked when an item renders

- `/i/270`, `/i/292`, and `/i/302` answered `200` with a fully rendered body while carrying no `published` label, so none of them appeared in the list. One is a personal record and two are scratch items, which means counting from `/i/1` to `/i/321` walked the whole of a private archive. All three now answer `404`, and `/i/321` and `/i/1` still render.
- Two things had to line up. `getIssueByNo` called `issues.get` and returned whatever came back, checking neither `state` nor the publish gate — the gate was applied by `getIssues` when building the list, and an item fetched by number never passed through it. And `generateStaticParams` prerenders only published items, but Next's `dynamicParams` defaults to `true`, so a number missing from that set is not a 404: it is a page rendered on demand.
- The gate went into `getIssueByNo` rather than into the page. It has one caller, and nothing else in the app fetches a single issue, so there is no consumer that wants the ungated version. A GitHub 404 and a gate rejection both come back as `null`, which let `loadIssue` drop its `status === 404` sniffing: three reasons for a bad URL now take one path.
- Reasoning and the options that were turned down are in `docs/adr/0003-the-publish-gate-is-checked-when-an-item-renders.md`. `dynamicParams = false` was the tempting one-liner and is worth having as a second layer, but not as the only one — it makes the reason for the 404 "it was not in the build" instead of "it is not published", and an item published between deploys would 404 until the next build.
- Noted while verifying: `#302` appears in this changelog's heading-rail entry as a test case for an item with no headings. An unpublished item was reachable while the site was being worked on, and that is how it was used. Checking one now means running the app locally.

## 2026-09-03 - Class names merge through `cn`

- `lib/utils.ts` now re-exports `cn` from the package of that name instead of composing `clsx` and `tailwind-merge` itself, and those two packages are dropped. `cn` is shadcn's own compiled drop-in for the pair, published 2026-09-02 from `shadcn-ui/cn` — worth noting because `cn` is a generic enough name on npm to deserve a second look, and because the package ships a `bin` (a CLI for compiling its class tables) which reads oddly for a class-name helper.
- Conflict resolution is the part of that pair this codebase actually leans on, so the swap was checked against the behaviour it replaced rather than taken on the strength of "drop-in". The toc panel overrides the popover's own `w-72`, `p-4`, and `gap-4`, and a tick's colour depends on `bg-foreground` beating `bg-muted-foreground`; every override resolves identically, including arbitrary values such as `max-h-[calc(100dvh-2.5rem)]` and pairs that must _not_ collapse, such as `text-muted-foreground` alongside `data-[active=true]:text-foreground`. Class merging happens at runtime, so a build cannot catch a regression here: confirmed in the rendered page as well, where the panel still computes to 240px wide with 4px of padding and a 0px row gap, and the ticks still measure 12px and 10px with exactly one filled in.
- `format:check` caught the one real problem, a semicolon on the new export line against this repo's `semi: false`. Fixed in place.

## 2026-09-03 - The item's headings become a rail in the left gutter

- Replaced the item page's table of contents. The 286px "On this Page" panel in the right gutter and the `Index` back-link in the left gutter are both gone, and in their place a rail of ticks sits pinned to the middle of the left gutter — one tick per heading, a step shorter for every nesting level, with the tick for the heading in view filled in. Clicking the rail opens the headings as a 240px list. The shape follows [Substack's article TOC](https://addyo.substack.com/p/agentic-skill-decay) closely: 12px ticks 1.5px tall, 2px shorter per level, 12px apart, `left: 8px`, vertically centred.
- The reason for the swap is that the old layout spent both gutters on navigation an item page barely needs. The right panel listed every heading permanently at the cost of a third of the page's width, and the `Index` link duplicated the `TMT` link already sitting under the title. The rail costs 28px and reads as a position indicator first, a menu second.
- The rail opens on click and then stays put. Picking a heading navigates without dismissing the panel, so several jumps in a row cost one click each, and only `Escape` or a click outside closes it. Hover does nothing but light the rail's own background. That is Substack's contract, checked against the page rather than assumed: a real pointer hover leaves its trigger at `data-state="closed"`, and its menu is still `open` after a heading has been picked.
- Rebuilt `components/toc.tsx` as one component, `TocRail`, and it needs no interaction state. It renders fumadocs' `AnchorProvider` itself and reads the active heading through `useActiveAnchor`, so the `TOCContext` that used to carry the heading list from the page down to a separate renderer is gone, and so is the page's `TOCProvider` wrapper — the page now passes the compiled `toc` straight in as `<TocRail toc={toc} />`. Base UI's Popover owns the click toggle, `Escape`, outside-click dismissal, and the focus handoff, and because picking a heading deliberately leaves the panel up there is nothing left for the component to control: the `<Popover>` is uncontrolled, and the file holds no state, no refs, no timers, and no mouse handlers. It is 77 lines whose only logic is the depth-to-indent mapping.
- Positioned the panel with `positionMethod="fixed"`, which needed a prop added to `components/ui/popover.tsx`. Base UI positions a popup absolutely by default, and the rail it anchors to is fixed to the viewport, so holding the panel still across a scroll meant rewriting its transform every frame — measured directly: over 2718px of scrolling the positioner's `translateY` moved 2718px in lockstep with `scrollY` purely to stay in place. Any frame the main thread missed against a compositor-driven scroll showed up as the panel sliding up and down. Positioning it the way the rail is positioned leaves nothing to recompute; the same measurement now reports a `translateY` delta of 0 across the same scroll, with the panel's on-screen rect identical to before. shadcn's `PopoverContent` forwards only `align`, `alignOffset`, `side`, and `sideOffset` to the positioner, so `positionMethod` joined that list — passed through rather than defaulted, leaving every other popover on Base UI's `absolute`.
- Deleted `components/clerk.tsx` along with `TOCScrollArea` and `TocThumb`. Those drew the vertical progress line down the right-hand panel by measuring anchor offsets and masking an inline SVG — about 140 lines of layout measurement that the rail has no use for, since a tick's own width and colour carry everything the line used to say. `lib/merge-refs.ts` existed only for them and went too.
- Nesting depth is measured from the shallowest heading present rather than assumed to start at `h2`. Item bodies are written by hand and start at whichever level the author chose, so a body whose headings begin at `h3` still gets a full-length tick for its top level.
- The rail is hidden below 1024px (`max-lg:hidden`). Substack's cut is 816px, but the article here is `max-w-[60ch]`, and around 900px the left gutter narrows to where the ticks start touching the text. Nothing was lost on small screens: the old right-hand panel was hidden below 1280px.
- One known limit: each tick occupies 13.5px, so an item with more than roughly 60 headings would run past the viewport. The longest item in the archive has 7. Substack does not clamp its rail either, so neither does this.
- Verified against a production build — 105 pages generated, no type or lint errors — and in the browser at 1440px with real pointer and keyboard input: ticks measure 12px for `h2` and 10px for `h3`, a real hover does not open the panel but still lights the rail, a click does open it, two headings can be picked in a row from one opening with the active tick and active row both following, scrolling neither dismisses the panel nor is locked by it, an outside click and `Escape` each close it with focus returning to the rail, panel rows indent 8px and 20px by level, and items with no headings (#1, #302) render no rail at all.

## 2026-09-03 - shadcn components move from Radix to Base UI

- Switched the shadcn component base from Radix to Base UI. The base is not a field of its own: it is chosen through `style` in `components.json`, whose enum now reads `radix-*`, `base-*`, and `aria-*` (React Aria) crossed with eight visual styles — `vega`, `nova`, `maia`, `lyra`, `mira`, `luma`, `sera`, `rhea`. This repo sat on the legacy `new-york` and now uses `base-vega`, whose button base classes (`rounded-md`, `focus-visible:border-ring`, `ring-3` at `ring-ring/50`, `text-sm`) are the ones the installed button already carried, so it is the smallest visual step of the eight.
- Replaced the five Radix packages and `cmdk` with `@base-ui/react@1.7.0`. Note that the published name is `@base-ui/react`; `@base-ui-components/react` is the older name and stopped at `1.0.0-rc.0`.
- Deleted `dialog`, `command`, `input`, `pagination`, and `scroll-area` from `components/ui/` instead of migrating them. Nothing in the app imported any of the five — they were vendored during setup and never used — and `@radix-ui/react-dialog`, `@radix-ui/react-scroll-area`, and `cmdk` sat in `package.json` only to serve them. What remains is `button` and a `popover` re-added from the new registry, which is the whole of the surface actually in use.
- `Button`'s `asChild` prop is gone, since Base UI composes through `render` rather than a `Slot`. Nothing broke: every caller here reaches for `buttonVariants()` and puts the classes on its own `Link` or `a`, and the one real `<Button>` passes only `onClick` and `variant`.
- One deliberate visual change comes along with it. The `destructive` variant is `bg-destructive/10 text-destructive` in the new design language rather than the solid `bg-destructive text-white`, so the "Try again" button on the item error boundary is now a tinted red rather than a filled one. All eight styles share that treatment, so it is not something the choice of `base-vega` could avoid.
- `app/globals.css` was left untouched by the CLI, verified by diff. Every variable the two components reach for — `--primary`, `--secondary`, `--muted`, `--border`, `--input`, `--ring`, `--destructive`, `--popover`, and `--radius-md` — was already defined there.
- The dependency count fell rather than rose: six packages out, one in. Verified with a production build of 105 pages and no type or lint errors.

## 2026-09-03 - The list moves to `/`

- Removed the redirects in `next.config.ts`: `/` no longer bounces to `/p`, and `/i` no longer bounces to `/i/1`. The list is served at `/` directly, and `/i` now 404s rather than landing on an arbitrary item.
- Moved `app/p/page.tsx` to `app/page.tsx`. The old root page was unreachable — the permanent redirect intercepted `/` before routing — and it held nothing but a link to `/p`. Every internal link in the app already pointed at `/` as home (`app/i/[issueNo]/error.tsx` and both `not-found.tsx` files), so those links now resolve directly instead of through a redirect hop.
- Moved `app/p/not-found.tsx` to `app/not-found.tsx`, which promotes it from a `/p`-segment boundary to the app's global 404. It now covers `/i` and any other unmatched path, where Next's default page used to show.
- Fixed a missing issue answering 500 instead of 404. `getIssueByNo` re-throws GitHub's 404, so the `notFound()` guard sitting below it was never reached and the error boundary answered instead — which also meant `app/i/[issueNo]/not-found.tsx` had never once rendered. `/i/abc`, `/i/0`, and `/i/-3` answered 500 too, from a `throw new Error("Invalid issue number")` guarding the parse. Both are bad URLs rather than server faults, so the route now answers 404 for either.
- The fix lives entirely in the route: `loadIssue` catches the fetch, calls `notFound()` when the caught error carries status 404, and rethrows everything else to the error boundary. `lib/github.ts` is untouched, so a network fault, a bad token, and a rate limit all keep travelling exactly as before.
- Collapsed the parse-validate-fetch sequence that `generateMetadata` and `IssuePage` each carried into one `loadIssue` helper. That duplication is why the bug survived: both copies held a working `notFound()` guard underneath a throw that shadowed it, so fixing one would have left the other.
- Known noise from leaving the data layer alone: `getIssueByNo` still logs `failed to fetch(fetchIssue)` with a stack trace before rethrowing, so a normal 404 writes two error lines per request — one from `generateMetadata`, one from the render. Silencing it would mean branching on the status inside `lib/github.ts`, which this shape deliberately avoids.
- Verified against a running build: `/` returns 200 with all 100 list links and `/i/321` and `/i/1` return 200, while `/p`, `/i`, `/i/99999`, `/i/abc`, `/i/0`, and `/i/-3` all return 404 rendering the app's own not-found page.
- One consequence to be aware of: the removed `/` → `/p` redirect was `permanent: true`, which browsers cache as a 308 with no expiry. A returning visitor may still be sent from `/` to `/p` by their own cache and land on a 404 until they clear it. Nothing in the app can undo a cached 308 — the options are to live with it or to serve `/p` again temporarily.

## 2026-09-03 - The `published` gate and secondthought's work queue

- Renamed the publish gate from `learn` to `published`. GitHub's label rename was used rather than creating a new label and re-applying it, so the label stayed attached to all 293 items. `learn` ("Today I learned") had nothing to do with whether something was published, and `published` sits in exact opposition to the existing `draft` (ADR 0002).
- Split labels into three namespaces by owner: unprefixed labels (`published`, `draft`, `secret`) belong to a human, `topic/` and `secondthought/` belong to secondthought. One rule — **a label containing a `/` belongs to the machine, one without belongs to a human** — defines the agent's entire write scope, and no misjudgment on its part can reach the publish gate or `secret`.
- Created the eight `topic/` labels plus `secondthought/needs-topic` and `secondthought/skipped`. A queue label needs an exit, which is why `skipped` exists: leaving an undecidable item (no body, or a personal record outside the topic axis) in the queue would keep the queue from ever emptying.
- Brought the app onto the new label scheme. `lib/labels.ts` holds the gate constant and the `topic/` display-name map, and `lib/github.ts` replaced the hardcoded `"learn"` and its `// TODO` comment with a constant reference. `app/p/page.tsx` now selects only `topic/` labels, draws them under their display names, and hides state labels. Alongside that, the eight lines of label normalization duplicated across two functions collapsed into `toLabelNodes`, which filters nameless labels at the data layer so the render side never handles `string | undefined`.
- Found and fixed a separate omission bug while verifying. Item #109 "Augmented Coding: Beyond the Vibes" demonstrably carried the gate label yet was missing from label-filtered queries, so it was not appearing in the site's list. Its timeline shows the label removed and re-applied on 2025-08-27, and GitHub's filter index appears to have gone out of sync from that point. The omission predates the rename and is unrelated to it; toggling the label once more forced a re-index and resolved it.
- Built the topic-labeling work as the `.agents/skills/applying-topic-labels/` skill and linked it into `.claude/skills/` by relative symlink. The skill is deliberately not named after the agent: the skill is the work and `secondthought` is what will do the work automatically, and calling both by one name would blur the distinction once the GitHub Action lands. Judgment points at `docs/design/topic-taxonomy.md` as its single source of truth, while the mechanical parts — querying and applying — live in `scripts/queue.ts` (`status`/`enqueue`/`list`/`show`/`apply`/`skip`). Queue lookups fetch every issue and filter locally rather than using `gh issue list --label`, because #109 showed the label filter index cannot be trusted.
- Four real items were classified while verifying the skill: `topic/frontend` on #155 "React 19.2" and #230 "현대(Modern) 브라우저는 어떻게 동작하는가?", `topic/platform` on #297 "어떤 규모에서도 동작하는 Git", and `secondthought/skipped` on #302 `dump`.
- Narrowed the classification scope to items past the publish gate. `secret` items (a résumé, a travel note) and `draft` items never reach the site, so they need no topic, and most fall outside the topic axis entirely. That removed the busywork of queueing such items only to pull each one back out as `skipped`.
- Rewrote the classification CLI from shell to TypeScript on bun (`scripts/queue.sh` → `queue.ts`). The reason was duplication: the list of eight topics existed in both `lib/labels.ts` and the shell script, so adding one meant editing two files, and editing only one would leave the app displaying a topic the script rejects. `lib/labels.ts` is now the single source of truth and the CLI imports it, with `TOPIC_LABELS` and the `TopicLabel` type derived from `TOPIC_DISPLAY_NAMES`' keys so the lists cannot drift.

- Two classes of shell bug disappeared structurally: jq rejecting unquoted non-ASCII object keys, and `head -c` cutting UTF-8 by byte and splitting characters. `show` now slices by code point, so emoji are safe as well. On top of that, the retry and throttling plugins bundled with octokit handle rate-limit backoff automatically. Writes stay serial, as GitHub advises.
- Queued 292 `published` items (of 293; #155 already carried a topic). None of the 26 items that had not passed the gate entered the queue, and no in-scope item is left without either a queue label or a topic. Bulk application POSTs to the labels sub-resource so it touches no other label, collects individual failures rather than aborting, and leaves only the failures behind on a re-run — so an interrupted run can be picked back up.

## 2026-09-03 - A record-keeping structure and a settled topic taxonomy

- Made this repository the home of the project's record: terminology in `CONTEXT.md`, hard-to-reverse decisions in `docs/adr/`, reversible design in `docs/design/`, and visible change in this file. Publishing decisions as `TMT-items` issues (dogfooding) and a single `DECISIONS.md` were both considered and dropped — the former cannot be `grep`ed, `diff`ed, or reviewed with the code, and the latter cannot link to one decision on its own (ADR 0001).
- Separated labels into a topic axis (`topic/*`) and a publish/state axis (`learn`, `draft`, `secret`). 293 of 319 items carried nothing but `learn`, and the app gated publication on exactly that label, so the choice was to lay a new namespace alongside rather than change what the existing label means (ADR 0002).
- Settled on eight topic categories: `topic/agents`, `topic/platform`, `topic/work`, `topic/context`, `topic/frontend`, `topic/craft`, `topic/agent-tools`, `topic/models`. All 319 items were analyzed to arrive at them, and the reasoning and boundary rules live in `docs/design/topic-taxonomy.md`. One primary label with up to two secondary labels is allowed because only 37 items land in exactly one category by keyword, which means a mutually exclusive single classification does not hold.
- Left open at this point: the app needed a `topic/` label to display-name mapping, since `app/p/page.tsx` drew `label.name` directly as a chip and applying labels would have exposed the string `topic/agents` in the list. secondthought's workflow also has to live in `TMT-items`, where the issue events happen.
